# Blockchain-Based Library Book Lending Tracker

## 1. Purpose and implementation scope

This project implements a local C11 simulation of a blockchain-backed university library. Its main purpose is to replace an editable lending log with a sequence of linked, proof-of-work blocks whose lending records are checked against book, member, and physical-copy registries. It combines registry loading, lending requests, a pending pool, block mining, token accounting, and disk persistence. It is a single-process educational application: it does not claim distributed consensus, network replication, or protection against a privileged user who can replace every local file and key.

The program uses fixed-capacity arrays for registries, copies, pending requests, and blocks. This keeps the underlying structures visible and easy to inspect in C, at the cost of configured limits and larger in-memory objects. The principal capacities and policy values are named constants in `src/main.c`, rather than scattered literals. Books and members are loaded from CSV text files; physical copies are loaded from `copies.txt`. The system checks field lengths, IDs, duplicate registry IDs, and copy-to-book references when loading.

## 2. Block and lending-record architecture

A block contains an index, strictly increasing Unix timestamp, record count, up to eight lending records, previous-block hash, Merkle root, sealing identity, aggregate return reward, reward transaction ID, proof-of-work difficulty, proof-of-work nonce, and final SHA-256 hash. The genesis block has index zero, no lending records, and a previous-hash value consisting of 64 zeroes. A mined block points to the prior block's stored hash. Its timestamp is advanced beyond the previous timestamp if two blocks would otherwise receive equal timestamps.

A lending record stores its deterministic record ID, book and copy IDs, title snapshot, member ID and name snapshot, action, reason code, due date, fine, member nonce, return reward, and ECDSA signature. New record signing and leaf hashing include the action; this is important because a change from `BORROWED` to `RETURNED` must not leave the signature unchanged. The record ID is recomputed from canonical record data before accepting a block. The block header hash includes the block fields and each record's signed leaf hash.

The Merkle tree is implemented directly in C. First, SHA-256 is calculated for every canonical signed record. At each level, neighboring hexadecimal digests are concatenated and SHA-256 hashed to form a parent. If a level has an odd number of nodes, its final node is paired with itself. The process repeats until one digest remains. A zero-record genesis block uses the SHA-256 digest of the empty string. Chain validation recomputes every non-genesis root and compares it with the root committed in the block.

Validation also checks block indices, previous-hash continuity, strict timestamp ordering, record-count bounds, record IDs, action and value constraints, referential integrity, record signatures, Merkle roots, block hashes, proof-of-work prefixes, reward totals, and reward transaction IDs. The `tamper` command alters a temporary in-memory copy of a block and runs validation against that copy; it does not modify the saved chain. The `validate` command reloads the saved chain and validates that disk copy. The CLI gates normal operations after a failed disk validation until the user invokes validation again.

## 3. Registries, physical copies, and reservations

The book registry maps book IDs to titles and authors. The member registry maps member IDs to full names and course codes. The separate copy registry maps a copy ID to its title ID, condition, state, current holder, due date, and renewal count. This distinction means that one title can have several copies with independent loan states. The application supports runtime book and member registration, and `add_copy` adds a runtime copy. Book and member registrations are appended to their CSV registry files. Member names entered through the current token-based CLI should use underscores in place of spaces.

The active inventory transitions include available copies being borrowed, borrowed copies being returned to availability or offered to a waiting member, lost-copy overrides that require a reason, and reason-coded condition updates. A return checks that the member holds the selected copy. Renewal checks ownership, the fixed maximum renewal count, whether another member is waiting, and whether the loan is already overdue. Loan and renewal periods are fixed at fourteen days in the current configuration.

Reservations are held in a FIFO queue by title and timestamp. A reservation is accepted when no copy is available. On return, the oldest reservation for the title is removed from the waiting queue and the copy is assigned to that member as reserved, rather than being generally available. The member can then borrow the offered copy. `reservations` and `reservation_status` display waiting reservations and copy offers. Copy states, reservation entries, and signed pending records survive restarts in `library_state.dat`; on startup, mutable copy state is cross-checked against the most recent confirmed and ordinary pending records.

Overdue scans run at startup and through the `overdue`/`check_overdue` commands. For a copy past its due date, the program calculates one fine unit per overdue day and queues one `OVERDUE` record for a loan and due-date pair rather than creating a duplicate on every scan. A return after the due date receives a late-return reward of five gross coins; an on-time return receives ten gross coins. A loan that has not been returned earns no return reward.

Fine settlement is represented by a separate signed `FINEPAID` record. The librarian submits a member, copy, and positive amount; the amount cannot exceed the oldest unsettled fine period. The event enters the same pending pool and cannot reduce outstanding debt until mined. Fine display combines overdue and late-return assessments for the same member/copy/due-date loan by taking the highest assessment, then subtracts both pending and confirmed settlements. This avoids counting a single late loan twice when it has an overdue scan followed by a late return. The current flow treats settlement as an external payment event; it does not debit member tokens.

## 4. Pending requests, nonces, and fraud review

Lending requests enter the persisted pending pool before mining. The miner orders overdue/fine-related requests before ordinary requests and sorts equal-priority work by submission time. It can include at most eight records in one block and continues with further blocks when more than eight eligible requests are waiting. Requests marked suspicious are excluded from the eligible set.

Confirmed lending records use a per-member nonce sequence beginning at zero. Confirmation order determines the final nonce values: the miner recalculates each eligible record's nonce and re-signs it before mining. The confirmed chain is the source for the next expected nonce. A pending request can therefore be re-numbered at confirmation instead of incrementing the confirmed member nonce merely because it was submitted.

The implemented misuse checks flag a borrow when the member already has five copies in the borrowed state or when the same member has a confirmed return of that title within 24 hours. A condition change that worsens a copy by more than one enum level without a reason beginning `OVERRIDE:` is also flagged. Condition events are signed with the librarian key, store the target condition in the event, and do not change inventory while suspicious. A flagged request receives `SUSPICIOUS` status, is displayed by `fraud_review`, and cannot be mined without explicit approval. Approval of a suspicious borrow rechecks availability; approval of a suspicious condition event applies its requested condition. Rejection removes the request. IDs can be entered as a unique prefix or as a complete request ID. The review status and associated record are saved across restarts.

These checks are heuristics, not proof of fraud. The condition detector is exposed as an explicit condition-update operation rather than inferring physical condition changes from a return, and the system does not provide a comprehensive request deduplication policy for every semantically equivalent action. The configured concurrent-borrow limit is five.

## 5. SHA-256, ECDSA, and replay protection

OpenSSL `libcrypto` supplies SHA-256 and ECDSA operations. Member keys use the P-256 elliptic curve. The program creates a private PEM key for each registered member at `member_<ID>_key.pem` and writes its corresponding public PEM to `member_<ID>_public.pem`. The member ID on the record selects which public key is used for signature verification. A librarian-authenticated lost-copy override is signed with the librarian key in `signing_key.pem`. `member_key ID` displays a member's public key. Private keys and generated ledger state are ignored by Git and must not be distributed as source-controlled files.

The signature covers the canonical record fields, including the action, record ID, member identity, due date, fine, reason code, and nonce. Ordinary lending and token-transfer events are member-signed; lost-copy and condition-override events use the librarian key. Block validation checks the appropriate verification key and fails closed for a record that does not verify. The application retains verification compatibility for records from older formats during migration; migrated chain records are re-created with action-bound signatures and re-mined using the new format. This format upgrade is needed because historical records used a weaker canonical payload.

The key files are local application data, not a hardware-backed identity system. The public PEM is stored alongside the local application state rather than embedded as a PEM blob in each on-chain record. The chain record binds the member ID and signed record fields, and the program resolves the member ID through the local key registry. Secure key backup, key rotation, revocation, and authenticated registration of public keys are outside this local demonstration.

## 6. Token models and mining

The process selects either `--model utxo` or `--model account`. In both models, confirmed returns create the member's spendable reward after a one-coin fee. Token transfers are ECDSA-signed and enter the same pending pool as lending actions; available funds are reserved logically while pending, but balances change only after a transfer record is mined. In the account model, each account has an integer balance and outgoing nonce. A transfer checks the supplied next nonce and available funds before it is queued; confirmation applies the debit, fee, credit, nonce increment, and linked-list history. In the UTXO model, confirmation selects enough currently unspent outputs, marks them spent, creates a recipient output, and creates a change output when needed. The signed chain transfer record commits the sender, recipient, amount, fee, accounting model, and account nonce where applicable. It does not enumerate each spent UTXO input and output as separate fields, so UTXO transaction-object completeness remains a limitation. `utxos` displays the currently unspent outputs.

Difficulty is a command-line option from one to four leading zero hexadecimal characters. The proof-of-work loop recomputes the block hash while incrementing the block nonce and reports the attempt count. Solo mode requires one registered member payout ID and credits the fixed two-coin reward for each mined block. Pool mode accepts two to four distinct registered member IDs, samples attempt attribution according to their simulated hash rates, and credits each member's measured share after deducting the 2% fee. Because the token APIs store whole coins, fractional shares accumulate in a per-member remainder persisted in the model-specific snapshot; they become spendable when the remainder reaches a whole coin. Cloud mode accepts one to five rounds and requires a registered recipient. It credits two gross coins per round and reports rental/maintenance fees, cumulative net, and unprofitable-round warnings. The operating costs are simulation expenses and are not debited from the token ledger. Mining payouts and pool contribution details are stored in the model-specific token snapshot, not committed into block fields, so deleting that snapshot prevents reconstruction of those payouts from the chain alone.

## 7. Persistence and CLI

`blockchain.dat` contains a nine-byte format magic, the block count, and fixed-layout block data. Versions `LIBCHAIN1`, `LIBCHAIN2`, and `LIBCHAIN3` are supported for migration; current writes use `LIBCHAIN4`, whose signed records include the action. `library_state.dat` stores copies, reservation entries, and pending records. `token_state_account.dat` and `token_state_utxo.dat` store separate model snapshots, including balances/nonces/history or the UTXO set. A token snapshot includes the chain count and tip hash to which it applies. `chain_metadata.dat` stores the current difficulty and fixed block reward separately from the block list. A `--difficulty` startup argument overrides and persists the stored difficulty, while `set_difficulty` changes it during a session. A corrupt or mismatched token snapshot stops startup rather than silently overwriting transfers or balances. Files are written via temporary files followed by rename.

The CLI covers book/member registration and views, copy inventory, borrow/return/reserve/renew, overdue checks, lost-copy overrides, pending-pool review, mining, token balances, transfers, transaction history, chain viewing, saving/loading, tamper demonstration, and validation. Examples and command syntax are in `README.md`; the Mermaid data-flow and persistence diagram is in `DESIGN.md`.

The current persistence format is a local binary representation of C structures and is intended for this project on the same compiler/platform. It is not a portable interchange or network protocol. Difficulty is stored in metadata and in each mined block; the configured block reward is currently a fixed compile-time value that is also written to metadata as a consistency check, not a user-adjustable setting. Registry CSV additions persist, while dynamic copy additions persist through the library-state snapshot.

## 8. Testing scenarios

The code was compiled with GCC using `-std=c11 -Wall -Wextra -Wpedantic -O2` and linked against OpenSSL. The final warning-enabled build completed without compiler warnings. Scenarios were run in temporary working directories so that the repository's `blockchain.dat`, key, registries, and saved state were not altered.

**Scenario 1 — lending, signatures, and tamper detection.** Expected: a valid borrow and return are queued, mined, and linked; the member public key can be inspected; altering a block copy is rejected, while the saved chain remains valid. Actual: the fresh chain reached three blocks; normal validation reported `VALID`, `tamper` reported `INVALID`, and subsequent disk validation reported `VALID`. The displayed record signature validated.

**Scenario 2 — suspicious re-borrow and account persistence.** Expected: a member who re-borrows the same title within 24 hours is held as suspicious, is not mined until approved, and a queued account transfer and nonce survive restart. Actual: the request appeared in `fraud_review` with the `rapid-reborrow-within-24h` reason. It was approved and mined; a later three-coin transfer with a one-coin fee stayed pending until the next mining operation. After restart, the account snapshot restored ALU001 at five coins with next nonce one and ALU002 at three coins; transaction history and chain validation were present.

**Scenario 3 — UTXO transfer and restart.** Expected: a confirmed nine-coin net return reward can fund a queued transfer of three coins plus fee; after mining, it creates the recipient output and sender change and survives restart without double spending. Actual: the transfer remained pending with balances unchanged until mined, then left a three-coin output for the recipient and a five-coin change output for the sender. Deleting only the temporary model snapshot and restarting reconstructed the same outputs from the chain, preserved transaction history, and validated the chain.

**Scenario 4 — format migration.** Expected: an existing version-3 chain is migrated to the new action-bound format and then validates. Actual: an isolated prior-format fixture printed the migration notice, persisted `LIBCHAIN4`, and passed full chain validation after restart.

**Scenario 5 — mining difficulty persistence.** Expected: a difficulty changed in one process is restored on the next launch, unless explicitly overridden on the command line. Actual: a temporary-ledger session changed difficulty from 2 to 3; the next launch displayed 3, and a launch with `--difficulty 1` displayed 1.

**Scenario 6 — mined fine settlement.** Expected: a signed partial payment remains in the pending pool until mined, reduces the assessed balance only after confirmation, and does not double-count an overdue record and a late return for the same loan. Actual: a focused integration fixture queued two partial payments for a past-due loan, mined each payment, validated the resulting two-block chain, and observed the outstanding fine fall from two to one and then to zero.

**Scenario 7 — condition downgrade review.** Expected: a multi-level condition downgrade without the override reason prefix remains suspicious and does not change inventory until approved. Actual: a new copy was registered as `NEW`; changing it to `WORN` was held as `SUSPICIOUS`, then approval applied the condition, mining validated the signed record, and a restart restored `WORN`.

**Scenario 8 — explicit mining payouts.** Expected: solo, pool, and cloud mining reject non-member payout IDs, credit the selected registered members, display contribution and cloud economics, and persist the resulting state through restart. Actual: solo mining credited ALU001 two coins and restored its history after restart. In the final two-member pool test, ALU001 contributed 46.67% and ALU002 53.33% of measured attempts; the displayed credited shares were 0.9147 and 1.0453 coins after the 2% fee, and both fractional transaction histories/remainders survived restart. A two-round cloud run credited ALU003 four gross coins in UTXO mode, reported six coins in costs and a negative-two net with warnings, and restored the four-coin output after restart. Rental/maintenance amounts are economic simulation costs, not token debits.

These tests exercise representative success and integrity paths. They are not exhaustive coverage of every assignment requirement or every malformed/corrupted state.

## 9. Remaining work against the complete rubric

This implementation is materially more complete, but it is not yet a literal implementation of every requested feature. Important remaining work includes: mining payouts and pool contribution details are not committed to block data and cannot be rebuilt from the chain if a token snapshot is lost; UTXO transfer inputs and outputs are not committed as a complete transaction object in the chain; and the fraud detector needs a complete duplicate-request policy. Cloud rental/maintenance costs are reported as off-ledger simulation expenses rather than debited from member balances. The specified public-key identity should be committed directly or immutably referenced in each on-chain record, rather than relying only on the local member-key files. In addition, a fully configurable renewal period and comprehensive automated test suite should be added.

The existing screenshots in `screenshots/` are CLI-output evidence, not a video recording. A 5–10 minute demonstration must be recorded separately. These remaining deliverables and feature gaps should be closed before claiming that the project fully meets the assignment rubric.
